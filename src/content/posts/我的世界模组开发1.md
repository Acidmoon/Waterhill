## 引言

一个 Minecraft 玩家想往游戏里加一个新物品，放在 2009 年，他得打开 `minecraft.jar`，删掉 `META-INF`，祈祷不要和别人的修改冲突。十七年后，同样的目标只需要 5 行 Java 代码和一个 Gradle 任务。从直接编辑字节码到声明式注册，从无法共存到上千模组协同工作——Minecraft 模组开发的历史，就是一部玩家如何一步步"接管"自己游戏的控制权的历史。

本篇知识大全为想写模组的人准备。不只是罗列知识点，更是帮你在 Forge、Fabric、NeoForge 之间做选择，理解 Mixin 什么时候该用什么时候不该用，知道报错了该翻哪篇文档。读完它，你应该对"写一个模组需要什么"有一个完整的认知地图。

## 1. 模组开发历史与演变

### 1.1 前加载器时代（2009–2010）

Minecraft 于 **2009 年 5 月** 首次公开发布（Classic 阶段），当时没有任何模组支持。直到 2010 年的 Alpha 阶段，玩家才开始尝试修改游戏。

**JAR Modding（Jarmodding）** 是唯一的模组安装方式。玩家需要直接编辑 `minecraft.jar`，替换 `.class` 文件，并手动删除 `META-INF` 文件夹以绕过数字签名验证。不同模组如果修改了同一个 `.class` 文件就会直接冲突，无法共存。

**hMod**（由 hey0 开发）是第一个重要的服务端框架，Bukkit 的前身。**Mod Coder Pack（MCP）** 由 Michael "Searge" Stoyke 等人创建，提供了反混淆映射表，使模组开发变得可行（Searge 后来被 Mojang 雇佣）。

### 1.2 第一代加载器（2010–2011）

**Risugami's ModLoader**（2010 年底发布）是第一个标准化的模组加载 API。它作为单一"基础模组"，其他模组通过"挂钩"方式接入，首次实现了多模组共存。ModLoader 一直维护到 Minecraft 1.6.2。

**Bukkit**（2011 年启动）提供了纯服务端的插件 API——服务器管理员可以修改服务端行为，而客户端无需安装任何内容。Bukkit 后来衍生出 Spigot 和 Paper。

### 1.3 Forge 统治时代（2011–2018）

**Minecraft Forge** 于 2011 年 11 月发布。最初不是加载器，而是由 Eloraam（RedPower）、SpaceToad（BuildCraft）等主要模组作者创建的协作 API 库。**Forge Mod Loader（FML）** 由 cpw 开发，彻底取代了 ModLoader，引入动态加载、事件系统和生命周期管理。

**里程碑**：
- **1.7.10（2014）**：由于 1.8 的重大变更，成为首个"黄金版本"
- **1.12.2（2017）**：同样原因（1.13 扁平化），成为史上模组最多的版本之一
- **2014 年**：微软收购 Mojang，社区担忧但政策未变
- **2014 年**：SpongeAPI 启动，由原 Bukkit 团队成员创建

**LiteLoader**（Mumfrey 开发）作为轻量级客户端专用加载器出现（1.5.2-1.12.2），其 Mixin 框架理念后来深刻影响了 Fabric。

### 1.4 分裂时代（2018–至今）

**1.13 "The Flattening"（扁平化）**（2018 年 7 月）——将数字 ID + metadata 替换为命名空间字符串 ID（如 `minecraft:stone`），从根本上打破了所有现有模组。Forge 需要完全重写 FML，耗时数月。

**Fabric 诞生**（2018 年 12 月 10 日）——由 asiekierka、modmuss50 等人发布。核心设计：极简 Loader（约 50KB）、模块化 API、Mixin 驱动、CC0 许可证的 Yarn 映射、Intermediary 跨版本映射。Fabric 能在新快照发布后数小时到数天内适配，与 Forge 的数月形成鲜明对比。

**Quilt 分支**（2021–2022）：因 Fabric 治理分歧而分出的分支，与大多数 Fabric 模组兼容，但未能获得显著生态份额。

**NeoForge 分支**（2023 年 7 月）：治理模式分歧和长期的管理风格争议导致分裂。包括 FML 创建者 cpw 在内的绝大多数 Forge 开发团队集体出走，创建 NeoForge。对于 Minecraft 1.20.2+，NeoForge 事实成为 Forge 血统的延续。

**Mojang 官方映射**（2019 年 9 月）：Mojang 开始为每个版本发布官方混淆映射表。

### 1.5 现状格局（2026）

- **Forge**：主导 1.20.1 及以下版本的经典生态
- **Fabric**：主导新版本快速迭代和性能优化领域
- **NeoForge**：在高版本（1.20.2+）替代原 Forge 地位
- **跨加载器开发**：Architectury API、MultiLoader 模板
- **Sinytra Connector**：兼容层，允许部分 Fabric 模组在 NeoForge 上运行
- **稳定版本锁定**：1.7.10、1.12.2、1.16.5、1.20.1 是各时代的"黄金模组版本"

### 关键数据

| 年份 | 事件 | 影响 |
|------|------|------|
| 2009.05 | Minecraft 首次发布 | 游戏起点 |
| 2010 底 | Risugami's ModLoader | 第一个标准化加载器 |

## 2. 模组加载器深度对比

### 2.1 主流加载器概览

| 对比维度 | Forge | Fabric | NeoForge | Quilt |
|---------|-------|--------|----------|-------|
| 创建年份 | 2011 | 2018 | 2023 | 2021–2022 |
| Loader 大小 | 庞大（>1MB） | 极小（~50KB） | 中等（重构中） | 中等 |
| 核心技术 | ASM + Event System | Mixin | Mixin + Event System | Mixin |
| 映射系统 | 官方 Mojang 映射 | Yarn（CC0）+ Intermediary | 官方 Mojang 映射 | Yarn |
| 更新速度 | 慢（数周-数月） | 极快（数小时-数天） | 较快（1-2 周） | 中等 |
| 模组生态 | 最大（数万） | 第二大（快速增长） | 增长中 | 极小 |
| 最佳场景 | 经典大型整合包 | 性能优化 + 新版本 | 高版本大型模组 | Fabric 兼容替代 |

> **注**：上表中的启动时间和内存占用因硬件配置和模组数量差异极大，表中数字为方向性经验值（典型消费级配置：SSD + 16GB RAM 场景）。

### 2.2 Forge：历史最久、生态最大

**架构特点**：大而全的"瑞士军刀"，提供几乎所有 API——注册、网络、能源（Forge Energy）、流体、世界生成等。核心是事件驱动架构 + Capability 系统 + MDK 一体化 Gradle 插件。

**生态规模**：模组数量最多，涵盖 Create、Tinker's Construct、Thermal Series、Twilight Forest、Thaumcraft、AE2、Mekanism 等经典大型模组。整合包生态最为丰富。

**局限性**：启动慢、内存占用高、更新速度慢、历史遗留问题多、社区治理存在争议。

### 2.3 Fabric：轻量级、Mixin 驱动

**架构特点**：极简 Loader（约 50KB）+ 可选的模块化 Fabric API + Yarn 映射（CC0）+ Intermediary 跨版本映射 + Knot 类加载器。Mixin 为核心技术进行结构化代码注入。

**生态优势**：性能优化模组的首选平台——Sodium（数倍 FPS 提升）、Lithium、Iris（光影）、Distant Horizons、Phosphor。MASA 全家桶（minihud、tweakeroo、litematica）等生电辅助模组。更新速度在所有加载器中最快。

**局限性**：大型内容模组生态不如 Forge 丰富（但快速增长），缺乏统一的跨模组交互系统（如统一能源 API）。

### 2.4 NeoForge：Forge 分支、现代治理

创建于 2023 年 7 月，cpw 及原 Forge 核心团队（除 LexManos 外几乎全员加入）。目标是继承 Forge 优点，同时向 Fabric 的现代化和透明度看齐。架构上：Forge 代码库重构、内置 Mixin、采用 Mojang 官方映射。1.20.1 因软分叉（soft fork）策略，Forge 模组与 NeoForge 大部分兼容（个别模组需调整版本号声明）；1.20.2+ 已彻底分叉。高版本大型整合包（如 ATM10）优先发布 NeoForge 版本。

### 2.5 Quilt

基于 Fabric 代码库，提供 Quilt Standard Libraries（QSL）替代 Fabric API，以及 Quiltflower 反编译器。Fabric 兼容意味着大多数 Fabric 模组可直接运行，但 Quilt 独有模组数量极少。

### 2.6 跨加载器方案

- **Architectury API**：Gradle 插件 + 构建扩展 + 运行时库。项目分为 `common`（共享代码）、`fabric` / `forge` / `neoforge` 子项目。使用 `@ExpectPlatform` 处理平台差异。
- **FDD-XPlat（Unimined）**：基于 Fabric Loom 的跨平台构建工具。
- **MultiLoader 模板**：常配合 Stonecutter（预处理器）和 Forgix（JAR 合并）使用。
- **Sinytra Connector**：允许部分 Fabric 模组在 NeoForge 上运行，通过"Forgified Fabric API"翻译层实现。

## 3. 模组类型与分类体系

### 3.1 整体分类

```
Minecraft 扩展类型
├── 需模组加载器
│   ├── 内容模组（双端安装）：新增方块/物品/生物/维度
│   ├── 辅助模组（仅客户端）：性能优化/辅助工具/信息查询
│   ├── 服务端专用模组：Carpet、Lithium
│   └── 库/API：Fabric API、Architectury API
├── 服务端插件（纯服务端）
│   └── Bukkit / Spigot / Paper API
├── 原版自带
│   ├── 数据包：配方/战利品表/函数
│   └── 资源包：纹理/模型/音效/语言
├── 光影包（需光影模组）
└── 整合包：模组 + 配置 + 任务 + 自定义内容的集合
```

### 3.2 内容模组（Content Mod）

最强大、最普遍的类型——向游戏添加全新内容，通常需要双端安装。

| 子类别 | 代表模组 |
|--------|---------|
| 科技类 | Thermal Expansion、Mekanism、AE2、IndustrialCraft 2 |
| 魔法类 | Thaumcraft、Botania、Ars Nouveau、Blood Magic |
| 冒险类 | Twilight Forest、Ice and Fire、Advent of Ascension |
| 农业/食物 | Pam's HarvestCraft、Farmer's Delight |
| 装饰类 | Chisel、Decocraft、Macaw's Furniture |
| 存储类 | Iron Chests、Refined Storage、Storage Drawers |
| 交通/物流 | Pipez、XNet、Railcraft |
| 世界生成 | The Aether、Biomes O' Plenty、Oh The Biomes You'll Go |

### 3.3 辅助模组（Utility Mod）

仅需客户端安装，增强玩家体验而非修改核心逻辑。

| 类型 | 代表模组 |
|------|---------|
| 地图/小地图 | JourneyMap、Xaero's Minimap |
| 配方查询 | Just Enough Items (JEI)、Roughly Enough Items (REI) |
| 性能优化 | OptiFine、Sodium、Lithium、Phosphor、Distant Horizons |
| 辅助工具 | Mouse Tweaks、Inventory Tweaks、AppleSkin、Tweakeroo |
| 自定义调整 | CraftTweaker、KubeJS、ContentTweaker |

### 3.4 服务端插件（Server Plugin）

基于 Bukkit / Spigot / Paper API 运行，仅服务端安装。**无法添加全新方块/物品类型**，功能集中在领地保护、经济系统、反作弊、权限控制、小游戏逻辑等。

平台演进：hMod(2009) → CraftBukkit(2011) → Spigot(2012) → Paper(2014)

### 3.5 服务端专用模组

介于内容模组和插件之间——使用模组加载器但仅需服务端安装（客户端 vanilla 即可连接）。代表：**Carpet**（红石生电技术功能）、**Lithium**（服务端性能优化）、**ServerCore**。通过 Mixin 修改服务端代码，不添加新方块/物品/纹理。

### 3.6 整合包（Modpack）

早期玩家手动配置模组难度极高，整合包解决了兼容性和分发问题。发展：Technic/Tekkit(2012) → Feed The Beast(2012–至今) → CurseForge 时代(2014–至今)。类型：Kitchen Sink → 任务驱动型 → 专家模式 → 空岛/石块类 → 硬核生存 → 主题型。

## 4. 开发环境与工具链

### 4.1 必备工具

**JDK 版本**（截至 2026 年 5 月）：

| Minecraft 版本 | 推荐 JDK |
|---|---|
| 1.16 及以下 | Java 8 |
| 1.17 ~ 1.20.4 | Java 17 LTS |
| 1.21（当前最新） | Java 21 LTS |

> **提醒**：Mojang 有时在次要版本间升级 JDK 要求，请以官方文档为准。

**IntelliJ IDEA Community Edition** + **Minecraft Development 插件（MCDev）** 是最推荐的 IDE 方案。MCDev 提供 Fabric/Forge/NeoForge 项目自动生成、Mixin 自动补全、Accessor 代码生成、runClient/runServer 配置自动创建。

### 4.2 项目骨架

MDK 是官方提供的开发入门模板：
- **NeoForge MDK**：github.com/NeoForgeMDKs/MDK-1.21-ModDevGradle
- **Forge MDK**：files.minecraftforge.net
- **Fabric 示例模组**：github.com/FabricMC/fabric-example-mod

标准项目结构：
```
MyMod/
├── src/main/
│   ├── java/com/example/mymod/
│   │   ├── MyMod.java          # 主入口类
│   │   ├── ModItems.java       # 物品注册
│   │   └── ModBlocks.java      # 方块注册
│   └── resources/
│       ├── fabric.mod.json     # Fabric 模组描述
│       ├── META-INF/neoforge.mods.toml  # NeoForge 描述
│       └── mods.toml           # Forge 描述
├── build.gradle
├── gradle.properties
└── settings.gradle
```

### 4.3 Gradle 构建系统

| 特性 | ForgeGradle | Fabric Loom | NeoGradle |
|------|-------------|-------------|-----------|
| 插件 ID | `net.minecraftforge.gradle` | `fabric-loom` | `net.neoforged.gradle` |
| 映射方案 | Official / Parchment | Yarn / Mojang / Parchment | Official / Parchment |

Fabric Loom 提供 Yarn/Mojang/Parchment 映射、依赖重映射（`modImplementation` 自动重映射）、Jar-in-Jar（`include`）打包。

常见构建问题：中国内地用户配置 BMCLAPI 镜像或阿里云 Maven 镜像解决 Gradle 下载超时。

### 4.4 辅助工具

**Blockbench**（blockbench.net）：Minecraft 模组开发中最流行的 3D 建模和动画工具。支持 Edit/Paint/Animate 三种模式，导出 JSON/C Java 代码。关键插件：GeckoLib 插件、Player Animator 插件。

**Misode 生成器**（misode.github.io）：网页端数据包 JSON 生成器，可视化生成世界生成特性、噪声设置、密度函数、拼图结构等复杂嵌套 JSON。

**调试技术**：Mixin 调试用 `@Debug(export = true)` 导出 class 文件对比；断点调试直接在 runClient/runServer 中启动；日志系统使用 ModLogger（Fabric）或 LogManager（Forge）。

### 4.5 测试流程

- **runClient** / **runServer**：Gradle 任务或 IDE 运行配置
- **Gametest 框架**（1.19+）：Mojang 官方集成测试框架，在真实游戏环境中验证功能行为。与 JUnit/Mockito（纯逻辑单元测试）配合使用，覆盖不同测试层次。
- **多版本兼容测试**：使用 Git 分支管理不同版本代码

## 5. 核心技术架构

### 5.1 Mixin 系统

Mixin 允许在类加载时修改字节码，是 Fabric 和现代 Forge/NeoForge 的核心技术。（后续章节提到"Mixin"，指的就是这个系统。）

```java
@Mixin(MinecraftServer.class)
public abstract class ExampleMixin {
    @Inject(method = "loadWorld", at = @At("HEAD"))
    private void onLoadWorld(CallbackInfo info) {
        // 在目标方法开头注入代码
    }
}
```

**主要注解类型**：

| 注解 | 用途 | 风险 |
|------|------|------|
| `@Inject` | 在目标方法指定位置注入代码（最常用） | 低 |
| `@Overwrite` | 完全替换目标方法体（不推荐，易引发冲突） | 极高 |
| `@Redirect` | 重定向方法调用或字段访问 | 高 |
| `@WrapOperation` | 包装操作，可选择性调用原操作（推荐替代 @Redirect） | 中 |
| `@Accessor` | 暴露私有字段读写 | 极低 |

**关键规则**：
- 社区强烈建议避免使用 `@Overwrite`——技术上合法，但两个模组同时 `@Overwrite` 同一个方法时只有一个生效
- 优先使用 `@WrapOperation` 代替 `@Redirect`，多个模组可链式包装同一操作
- 仅在事件系统不足以满足需求时使用 Mixin

**Access Widener vs Mixin Accessor**：Access Widener 修改字节码可见性标识（可访问私有类、去除 final），Mixin Accessor 创建接口在调用侧转换（更安全）。简单场景优先使用 Mixin Accessor。

### 5.2 事件系统

**Forge 事件系统**——两个主要总线：
- **Forge Event Bus**（`MinecraftForge.EVENT_BUS`）：运行时游戏事件（伤害、方块破坏、交互）
- **Mod Event Bus**（`FMLJavaModLoadingContext.get().getModEventBus()`）：模组生命周期事件

使用 `@SubscribeEvent` + `@Mod.EventBusSubscriber` 注册，支持 5 级优先级，通过 `event.setCanceled(true)` 取消。

**Fabric 事件系统**——使用回调接口模式：
```java
PlayerBlockBreakEvents.BEFORE.register((world, player, pos, state, entity) -> {
    return true; // false 取消破坏
});
```

Fabric 使用 `InteractionResult` 返回值模式支持事件的链式处理。

### 5.3 注册表系统（Registry）

所有注册对象使用 `ResourceLocation`（`namespace:path`）作为唯一标识符。

**Fabric 注册**——直接使用 `Registry.register()`：
```java
public static final Item MY_ITEM = Registry.register(
    BuiltInRegistries.ITEM,
    Identifier.of(MOD_ID, "my_item"),
    new Item(new Item.Properties())
);
```

**Forge/NeoForge 注册**——使用 `DeferredRegister` + `RegistryObject`：
```java
public static final DeferredRegister<Item> ITEMS = DeferredRegister.create(ForgeRegistries.ITEMS, MOD_ID);
public static final RegistryObject<Item> MY_ITEM = ITEMS.register("my_item", () -> new Item(new Item.Properties()));
ITEMS.register(modBus); // 在 Mod 构造函数中
```

### 5.4 Capability 系统

**Forge Capability**——动态附加数据到游戏对象。三种内置：`IItemHandler`（物品）、`IFluidHandler`（流体）、`IEnergyStorage`（能量）。通过 `getCapability(Capability<T>, Direction)` 暴露。1.19+ 引入 `BlockCapability`、`EntityCapability`、`ItemCapability` 新 API。

**Fabric 的替代方案**：Fabric API 的 `Attachment` 系统（1.20.5+）、直接使用 NBT、第三方库如 Cardboard。

### 5.5 数据生成（Data Generation）

现代模组开发的标配技术，自动生成 JSON 资源文件。Fabric 通过 `DataGeneratorEntrypoint` + Provider 方案，Forge 通过 `GatherDataEvent`。运行 `./gradlew runDatagen`。

### 5.6 网络通信

Fabric（1.20.5+）使用 Payload 模式：定义 CustomPayload → 注册 PayloadTypeRegistry → 注册接收器。Forge 使用 `SimpleChannel`。Architectury 提供跨平台抽象 `NetworkManager`。

## 6. 核心内容开发

### 6.1 自定义物品

通过 `Item` 子类和 `Item.Properties` 配置。`.stacksTo()`（最大堆叠）、`.maxDamage()`（耐久）、`.food()`（食物属性）、`.rarity()`（稀有度）、`.fireproof()`（防火）。

**工具**：实现 `ToolMaterial` 接口，使用 `SwordItem`、`PickaxeItem` 等子类。
**护甲**：实现 `ArmorMaterial` 接口，使用 `ArmorItem` 子类。
**食物**：使用 `FoodComponent.Builder`（1.20.x）或 `FoodProperties.Builder`（1.21+）。

### 6.2 自定义方块

通过 `BlockBehaviour.Properties` 配置硬度、声音、发光等属性。需要配套的方块状态 JSON、模型 JSON、纹理、掉落表和语言文件。

**实体方块（BlockEntity）**：创建子类覆盖 `saveAdditional()` / `loadAdditional()` → 注册 `BlockEntityType` → 创建 `BaseEntityBlock` 子类 → 实现 `getTicker()`。

### 6.3 自定义实体

注册 EntityType → 配置 AI 行为（Goal 系统或 Brain 系统）→ 注册生成规则 → 注册渲染器。

### 6.4 自定义配方

简单配方通过 JSON 文件定义。自定义配方类型需要创建 Recipe 类 → RecipeSerializer（MapCodec）→ 注册 RecipeType 和 Serializer。

### 6.5 自定义世界生成

1.18+ 三层架构：Configured Feature（定义什么）→ Placed Feature（定义如何放置）→ Biome Modification（定义在哪）。

### 6.6 自定义维度

自 1.16 起完全由数据驱动。Java 端注册 RegistryKey → dimension_type JSON → dimension JSON → 传送门（Fabric 使用 Custom Portal API）。

---

## 7. 高级功能与系统

### 7.1 多方块结构（Multiblock）

**Multiblocked**——最强大的多方块创建模组（CleanroomMC/LowDragMC 维护）。核心特性：IO by Proxy、视觉编辑器、多种渲染器、异步线程。深度集成 CraftTweaker 和 KubeJS。其他方案：Sus MultiBlocked、Aquamarine、手动实现。

### 7.2 能源/流体/物品管道

**Forge Energy（FE）**：`IEnergyStorage` 接口（6 个方法），通过 Capability 附加。**Fabric Transfer API**：`Storage<T>` 泛型接口、`Transaction` 原子操作。

### 7.3 自定义 GUI/容器

三个核心组件：`AbstractContainerMenu`（服务端逻辑）+ `AbstractContainerScreen`（客户端渲染）+ `MenuType`（工厂）。

### 7.4 渲染与着色

BakedModel → BlockEntityRenderer（BER）/ BEWLR → HUD 覆盖（NeoForge 用 `IGuiOverlay`，Forge 用 `RenderGameOverlayEvent`）→ 粒子效果。

### 7.5 数据同步与持久化

BlockEntity 用 NBT（`writeNbt`/`readNbt`），1.20.5+ 可用 Data Component 系统（类型安全 Codec）。世界级数据用 SavedData。

### 7.6 配置系统

Forge/NeoForge：TOML 格式（`ForgeConfigSpec`），分 CLIENT/COMMON/SERVER 三级。Fabric：使用 Cloth Config API。

## 8. 数据驱动开发

### 8.1 原生数据包（Vanilla Datapack）

1.13 引入，无需模组加载器。存入 `datapacks/`，`/reload` 热重载。结构：`pack.mcmeta` + `data/<namespace>/`（advancement / loot_table / recipe / functions / predicate / tags 等）。

**函数自动执行标签**：`#minecraft:tick`（每刻执行）、`#minecraft:load`（加载时执行）。

### 8.2 资源包（Resource Pack）

控制客户端视觉和听觉：纹理（16×16 PNG）、模型（JSON）、声音（OGG）、语言文件（JSON）、方块状态、字体。

### 8.3 动态资源生成

YARRP（Fabric/NeoForge，Kotlin API）、ARRP/BRRP（老牌 Fabric 库）。

### 8.4 无代码模组方案

**KubeJS（JavaScript）**——最流行，支持 Forge/Fabric/NeoForge，可添加/修改配方、自定义方块/物品、修改标签等。**CraftTweaker（ZenScript）**——配方修改经典方案。**JSON Things**——纯 JSON 定义物品/方块/流体，无需 Java。

### 8.5 社区工具

Misode 生成器（misode.github.io）、MCDatapacker、Spyglass（VS Code 插件）、Blockbench。

## 11. 学习路径与实战建议

### 11.1 从零开始的推荐路径

**第一阶段：Java 基础（2-4 周）**
必须掌握：面向对象、泛型、注解、Lambda。推荐 Kaupenjoe 的 Java 入门课程或尚硅谷/黑马程序员免费教程。

**第二阶段：选择模组框架**

初学者推荐从 Fabric 入手（API 简洁、学习曲线平缓），但需要了解其局限性：Fabric 依赖 Mixin 实现许多原本需要内置 API 的功能，缺乏统一能源/流体 API。如果目标是做需要大量跨模组交互的大型项目，NeoForge 的事件系统和内置 API 更适合。不要同时学两个，先精通一个再迁移。

**第三阶段：入门（1-2 周）** → 第四阶段：核心系统（4-8 周）→ 第五阶段：高级功能 → 第六阶段：工程化与发布。

### 11.2 高质量学习资源

1. **Kaupenjoe 教程体系**（视频+GitHub+Udemy）— 入门→进阶
2. **Fabric 官方 Wiki**（中/英文档）— 入门→进阶
3. **Forge 官方文档**（英文）— 入门→进阶
4. **Flandre芙兰 B 站教程**（中文视频）— 入门→进阶
5. **mouse0w0 开发者指南**（GitHub 中文索引）— 全阶段
6. **NeoForge 官方文档** — 进阶
7. **《Minecraft 模组开发指南》**（中文纸质书）— 入门
8. **Create 源码 / AE2 源码** — 进阶

### 11.3 常见陷阱

- **版本兼容性**：严格确保 MC ↔ JDK ↔ 加载器版本对应
- **Mixin 冲突**：用完整方法描述符（`tick()V` 而非 `tick`），避免 `@Overwrite`
- **SideOnly 问题**：客户端代码被服务端加载导致崩溃，正确设置 `environment`
- **事件订阅错误**：理清 Mod 总线（生命周期）和 Forge 总线（运行时事件）的区别

### 11.4 成就清单

1. 了解模组基本结构 → 2. 选择目标框架 → 3. 搭建开发环境 → 4. 第一个物品（有贴图）→ 5. 第一个方块 → 6. 理解注册系统 → 7. 理解事件系统 → 8. 带 GUI 的机器 → 9. 发布到 CurseForge/Modrinth → 10. 收到反馈并修 Bug → 11. 阅读知名模组源码 → 12. 贡献代码 → 13. 参与 TeaCon

## ⚠️ 争议与局限

1. **加载器对比数据**：启动时间和内存占用的数据为经验性估算，不同硬件和模组配置下差异显著，不应作为技术选型的唯一依据。
2. **版本信息时效性**：Minecraft 版本更新频繁，JDK 兼容表和 `pack_format` 值可能随新版本发布而过时。
3. **社区信息来源**：部分 QQ 群号、教程集数、模组收录数等数据来源于社区，可能随时间变化。
4. **Forge/NeoForge 历史**：分裂事件涉及复杂的治理和技术争议，本文力求中立但无法穷尽所有视角。
5. **中文生态**：MCBBS 关站后中文社区处于重新整合期，平台活跃度和可用性可能变化。
6. **未覆盖主题**：本篇未深入覆盖基岩版 Add-on 开发、Minecraft 中国版专有 API、商业模组运营等方面。
